# 인식 코드 통일과 웹캠 디스플레이 — 수요일 MVP (설계)

2026-11-23(월) · 오늘 완성을 목표로 한다(MVP 마감 2026-11-25 수) · 브랜치: `main`에서 새로 딴다(`camera-ui`는 PR #2로 병합됨)

앞 문서와의 관계: `2026-11-16-display-link-design.md`의 "디스플레이를 Expo 웹으로 만든다"는 이 문서로 대체한다. 디스플레이는 지금처럼 서버가 내주는 HTML 페이지로 남는다. 테이크 좌표 녹화(`2026-11-16-take-recording-design.md`)의 코드는 `stash@{0}`에 있고, 이번 범위가 아니다.

## 왜 하는가
수요일까지 MVP를 만들고 같은 수업 사람들 앞에서 시연한다. **시연의 성공 기준**(사용자):
1. 시연자가 추는 동작을 디스플레이가 정확히 분석해서 보여 준다.
2. 캐릭터(AI 개입)가 지금 부족한 부분을 정확히 짚어 준다.

시스템의 짝(사용자): **카메라–디스플레이**, **폰–음악(음원 분리·레이어)**. 워치는 녹화 시작과 레이어 조절을 맡는다. 영상 촬영·저장·편집은 폰에서 한다.

지금 코드로는 기준을 채울 수 없다:
- **인식 코드가 두 벌이다.** 폰은 `app/src/tracking/`(id403에서 옮긴 TS, 정답 테스트 있음), 웹캠은 `server/app/movement.js`. "안 쓴 부위"의 정의부터 다르다(폰: 6부위 중 8.3% 미만이고 충분히 보인 부위만 / 웹캠: 팔다리 4개 중 12.5% 미만, 보였는지 안 봄). 같은 춤이 카메라에 따라 다르게 읽힌다.
- **웹캠은 가려진 팔을 "안 쓴 팔"로 센다.** 가려진 관절을 마지막 위치에 멈춰 두기 때문이다. 확인함: 두 팔을 똑같이 흔들고 왼팔만 가리면 `underused: ["arm_l"]`, 가리지 않으면 `[]`.
- **웹캠만 쓰면 캐릭터가 끼어들지 않는다.** 서버 캐릭터(`display_agent.py`)의 조건이 "폰 세션에서 2분간 저장 안 함" 또는 "반복 구간 3번"이라 폰이 보내는 정보가 있어야 한다.
- 웹캠 페이지(`/movement`)와 디스플레이(`/display/<방>`)가 다른 페이지라 탭 두 개를 열어야 하고, 웹캠 영상은 디스플레이에서 볼 수 없다.

## 사용자가 정한 것
- 인식 코드를 **하나로 통일**하고, 이것을 먼저 한다.
- **웹캠이 기본**이고, **폰 카메라로도** 트래킹할 수 있어야 한다.
- 웹캠·디스플레이는 **폰 앱과 따로** 돌아야 한다. (작성자 해석: 컴퓨터에서 서버와 브라우저만 있으면 폰 없이 시연 흐름 전체가 돈다. 폰은 붙이면 음악 시계를 더해 줄 뿐이다.)
- 디스플레이에 **웹캠 화면을 디버깅용으로** 넣는다.
- 캐릭터가 짚는 범위: **A 팔다리 중 안 쓴 쪽 + B 공간·높이.**
- 캐릭터는 **먼저 묻고, '예'라고 답할 때만** 제안을 보여 준다. '예'의 방법으로 사용자가 생각 중인 것: 워치에 뜬 팝업에서 OK, 또는 **두 팔로 머리 위에 O를 만들어 3초 이상** 유지. **'아니요'는 일정 시간 안에 O가 없는 것**으로 한다.
- 디스플레이 글자는 **모두 영어**가 기본이다. 한국어로 바꾸는 기능은 있으면 좋다.
- 시연 동작은 이 흐름이 확실히 보이도록 짠다.

아래 나머지는 **작성자의 판단**이고, 맨 아래 "작성자의 판단 목록"에 모았다.

## 목표 (수요일 MVP)
1. `app/src/tracking/`이 하나뿐인 인식 코드다. 웹캠 쪽 라벨(부위별 동작·질감·박자·공간)을 여기로 옮기고 `server/app/movement.js`는 없앤다.
2. 디스플레이 페이지 하나가 웹캠을 켜고 이 코드로 읽어서 그린다. 폰과 Expo 없이 서버 + 브라우저만으로 돈다.
3. 디버깅 화면: 웹캠 영상 + 스켈레톤 + 인식 값 + 캐릭터 타이머를 켜고 끈다.
4. 웹캠만으로도 캐릭터가 끼어든다. 짚는 것: 안 쓴 팔다리(A), 안 간 높이·좌우(B). 가장 오래 부족했던 것을 먼저 짚는다.
5. 캐릭터가 물으면 시연자가 손을 쓰지 않고 '예'라고 답할 수 있다(머리 위 O 3초).
6. 제안을 받은 뒤 그쪽을 해 보면 "해봤네요"(You tried it)로 알아본다.
7. 폰 카메라 경로도 같은 코드로 같은 값을 보낸다(node 테스트까지, 실기기 확인은 기기가 있을 때).
8. 시연 대본(동작 순서·길이·서는 자리) 문서.
9. (여유가 있으면) 디스플레이 글자를 한국어로 바꾸는 스위치.

## 하지 않는 것
- 테이크 좌표 녹화·테이크 보기(`stash@{0}`), 일곱 축 중 나머지(질감·박자·연결을 캐릭터가 짚는 것).
- 디스플레이 시안 반영(8-Body Heatmap 여섯 구역, 캐릭터 그림). 지금의 8자 화면을 유지한다.
- 폰이 관절 좌표를 디스플레이로 보내는 방식. 좌표는 찍은 기기 밖으로 나가지 않는다.
- 웹캠 영상을 폰으로 넘기기(나중에 하면 좋은 것).
- 안 쓰는 코드 정리(대부분 성원 님 파일). 이번 통일로 생기는 삭제(`movement.js`, `movement.html`)만 한다.
- 언어 모델(LLM). 캐릭터는 지금처럼 규칙 기반이다.
- 방 인증·암호화.

## 이렇게 되면 실패
- 가려지거나 화면 밖에 나간 부위를 "안 썼다"고 짚는다(원칙 4).
- 시연 중 캐릭터가 대본의 때에 뜨지 않거나, 너무 자주 떠서 춤을 방해한다.
- 춤 동작이 '예'(머리 위 O)로 잘못 읽혀 묻지도 않은 답이 들어가거나, '예'를 하는 동작 자체가 "해봤네요"로 읽힌다.
- '예'라고 답하지 않았는데 제안이 뜬다.
- 폰 경로의 숫자가 바뀌어 id403 정답 테스트가 깨진다.
- 웹캠 디스플레이를 돌리는 데 폰 앱 빌드, Expo, node가 필요하다.
- 영상이나 관절 좌표가 페이지 밖으로 나간다.
- 디스플레이가 점수판처럼 읽힌다(잘함/못함, 빨간색).

## 제약
- `app/src/tracking/`은 React 없는 TS이고 node로 테스트한다(`npm run test:tracking`). id403과 공유하는 설정 섹션과 정답 테스트는 건드리지 않는다. 새 값은 `config.ts`의 `app` 섹션이나 새 섹션에 둔다.
- 팀원은 맥에서 `server/./run.sh`만 돌린다. 디스플레이용 JS는 미리 묶어서 저장소에 넣어, 서버만으로 돈다.
- 자세 인식은 지금처럼 브라우저의 MediaPipe Pose lite를 CDN에서 받는다(인터넷 필요).
- 카메라 한 대, 2D 중심: 카메라 쪽으로 밀기·당기기, 제자리 회전은 보이지 않는다.
- 커밋은 사용자가 요청할 때만 한다.

## 고려한 방법 (무엇으로 통일하나)
| | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A** | **`app/src/tracking/`으로 통일.** 웹캠 라벨을 TS 모듈로 옮기고, 디스플레이용으로 브라우저 묶음 파일을 만든다 | 폰과 웹캠이 같은 코드. id403 정답 테스트가 계속 지켜 준다. `feedback.ts`의 부위·높이 제안과 "해봤네요"가 웹캠에도 온다. 이 코드는 4ff2a17에서 브라우저로 돌려 본 적이 있다 | 묶는 단계가 생긴다(`esbuild` 추가). `movement.js` 약 190줄을 옮긴다 |
| B | `movement.js`로 통일하고 폰이 이것을 불러 쓴다 | 디스플레이 쪽 변경이 적다 | `app/src/tracking/`의 8카운트 창, 세션 저장, 분석 탭, 캘리브레이션, 춤 시작, 정답 테스트를 대신해야 한다. 가장 큰 일이고 정답 테스트를 잃는다 |
| C | 폰은 관절 좌표만 보내고 디스플레이에서만 인식한다 | 실행 중 인식이 한 곳 | 폰 단독 카메라 탭에는 어차피 폰 안의 인식 코드가 필요하다(A 위에 덧붙이는 것). "좌표는 폰 밖으로 안 나간다" 원칙을 바꿔야 한다 |

**A로 간다**(사용자가 "통일 먼저"를 고름). C는 나중에 A 위에 더할 수 있다.

## 설계

### 1. 카메라 고르기 — 디스플레이의 세 가지 모드
| 모드 | 주소 | 누가 읽나 | 음악 시계 | 디버깅 화면 |
|---|---|---|---|---|
| **웹캠 단독 (기본)** | `/display` | 이 페이지(웹캠) | 없음. BPM을 입력하면 박자 라벨과 8카운트 점이 그것을 따른다 | 있음 |
| 웹캠 + 폰 세션 | `/display?room=<폰 방>` | 이 페이지(웹캠) | 폰(지금 커밋 안 한 `camera` 역할을 쓴다) | 있음 |
| 폰 카메라 | `/display/<폰 방>` | 폰 | 폰 | 영상은 폰 밖으로 안 나가므로 "폰의 카메라 탭에서 확인하세요"만 띄운다 |

- 웹캠 대신 **댄스 영상 파일**을 넣는 입력(커밋 안 한 변경)을 그대로 둔다. 리허설과 기준값 맞추기에 쓴다.
- `/movement`는 `/display`로 넘긴다. 폰 앱의 "Creative display" 주소는 그대로 동작한다.

### 2. 인식 — 무엇을 어디서 계산하나
| 값 | 어디서 | 비고 |
|---|---|---|
| 부위 사용량, 안 쓴 부위, 높이 비율, 8카운트 창, 캘리브레이션, 춤 시작 | 지금의 `app/src/tracking/` 그대로 | id403 정답과 같은 숫자 |
| 부위별 동작(hold/reach/circle/swing/shake, 몸통 shift/travel/jump/drop), 속도·크기·질감·박자, 전체 요약 | 새 `app/src/tracking/labels.ts` | `movement.js`를 옮긴 것. 테스트는 `server/tests/movement.test.mjs`의 경우들을 `app/scripts/tracking/labels.test.cjs`로 옮긴다 |
| 공간: 좌·중·우 구역, 높이, 앞뒤, 쓴 너비 | `labels.ts` | 처음에 가만히 선 자리를 기준으로 삼는다(지금과 같음) |
| 바닥 히트맵(8×8) | `app/src/projection/heatmap.ts` | 웹캠에서도 "Where you moved" 칸이 채워진다(캘리브레이션 전에는 카메라 화면 기준) |
| MediaPipe 결과 → 프레임 | `app/src/tracking/webEvent.ts` | 4ff2a17에서 되살린다 |

- **가려진 부위**: `labels.ts`는 충분히 보이지 않은 부위를 "모름"으로 두고, 비율 계산과 "안 쓴 부위"에서 뺀다. 마지막 위치에 멈춰 두는 방식은 없앤다. 위의 왼팔 가림 경우를 테스트로 넣는다.
- 분석 탭용 동작 횟수(`moves.ts`)와 `labels.ts`는 목적이 달라서(저장되는 횟수 / 지금 4초의 말) 이번에는 둘 다 둔다. 합치는 것은 나중 일이다.

### 3. 묶음 파일
- 새 `app/src/tracking/display.ts`: 디스플레이 한 프레임 처리의 입구. 웹캠 프레임을 받아 트래커, 라벨, 히트맵을 돌리고 **방으로 보낼 패킷 하나**를 만든다. 폰의 `ProjectionCard.tsx`도 같은 패킷 함수를 써서 두 경로의 모양이 같아진다.
- 새 `app/scripts/build-display.cjs`: `esbuild`로 `display.ts`를 ES 모듈 하나로 묶어 `server/app/static/tracking.js`에 쓴다. 결과 파일은 저장소에 넣는다. 테스트 하나가 "묶음이 소스와 맞는지"를 확인한다.
- 서버는 `/static/tracking.js`를 내준다.

### 4. 캐릭터 — A+B
**짚는 대상**
| 무리 | 대상 | 근거 값 | "부족"의 정의 |
|---|---|---|---|
| A | `arm_l` `arm_r` `leg_l` `leg_r` | 최근 30초의 부위 사용량 | 지금 트래커 규칙(`underused_ratio`, 충분히 보인 부위만) |
| B 높이 | `low` `high` | 최근 30초의 높이 비율 | 지금 `feedback.ts` 규칙(`level_min_share` 0.1 미만) |
| B 좌우 | `left` `right` | 최근 30초 동안 춤추는 사람 기준 왼쪽·오른쪽 구역에 있던 시간 비율 | 0.1 미만(새 값, 맞춰야 함) |

- 디스플레이 페이지가 위 대상 중 지금 부족한 것의 목록을 패킷의 `body.underused`에 실어 보낸다. 서버는 목록을 검사하고(`projection.py`의 허용 단어에 새 대상을 더함) 캐릭터에 넘긴다. 캐릭터는 **언제 말할지만** 정한다.
- **고르는 순서**: 부족한 상태가 가장 오래 이어진 대상을 먼저 짚는다. 같으면 A가 B보다 먼저다.
- **웹캠으로 읽을 때의 끼어들기 조건**: 사람이 보이고 15초가 지난 뒤, 한 대상이 8초 이상 계속 부족하면 묻는다. 묻기 사이는 30초, 같은 대상은 60초 띄운다. 값은 `MovementGuide`의 생성 인자로 둔다. 규칙은 **누가 춤을 읽느냐**를 따른다: 웹캠이 읽으면(웹캠 단독, 웹캠 + 폰 세션) 이 규칙, 폰 카메라가 읽으면 지금 규칙(2분 저장 없음 / 반복 3번). 그래서 나중에 워치 OK로 답하기로 정해도, 웹캠 + 폰 세션 모드에서 같은 때에 묻는다.
- **문장**(영어): `LocalPromptGenerator`에 `low` `high` `left` `right` 문장을 더한다. 지금 문장처럼 짧은 권유형이다(예: "Go low", "Explore your left side").

**묻기와 답하기**
1. 캐릭터가 "Need some help?"를 띄운다. 화면에 "Make an O over your head to say yes"를 같이 보여 준다.
2. '예'가 들어오면 제안 문장을 보여 준다. **묻고 12초 안에 '예'가 없으면 '아니요'로 본다**: 질문을 거두고 "Maybe later"를 잠깐 보인 뒤, 거절과 같게 쉬는 시간(30초, 같은 대상 60초)을 센다. 지금의 [Not now] 버튼(디스플레이·폰·워치)도 그대로 '아니요'로 쓸 수 있다. O를 만들기 시작했으면(채워지는 원이 진행 중) 12초가 지나도 끝날 때까지 기다린다.
3. 제안이 뜬 뒤에는 다시 답할 필요가 없다. 제안은 20초 보인다.

'예'가 들어오는 길:
| 길 | 쓸 수 있는 모드 | 이번 작업 |
|---|---|---|
| **머리 위 O 3초** | 웹캠이 읽는 모드 | 새로 만든다. 시연 기본 |
| 워치 팝업 OK | 폰이 방에 붙은 모드(웹캠 + 폰 세션, 폰 카메라) | 이미 있다(워치 알림 → 폰 → 서버). 바꾸지 않는다 |
| 디스플레이·폰 버튼, 키보드 `Y` | 모든 모드 | 버튼은 이미 있다. 키보드만 더한다(리허설용) |

**머리 위 O 알아보기**(새 `app/src/tracking/answer.ts`, node 테스트)
- 조건: 두 손목이 머리 꼭대기보다 위, 두 손목 사이가 몸통 길이의 0.6 이하, 두 팔꿈치가 어깨보다 위이고 손목보다 바깥. 관련 관절이 모두 잘 보일 때만.
- 3초 동안 끊김 없이 유지되면 '예'다. 화면에는 유지하는 동안 채워지는 원을 보여 준다.
- **캐릭터가 묻는 동안에만** 센다. 묻기 전에 만든 O는 세지 않고, 한 번 답한 뒤에는 팔을 내렸다가 다시 만들어야 다음 답이 된다.
- 웹캠 페이지가 알아보고 서버에 `agent_response`(accept)를 보낸다. 서버 쪽 처리는 버튼과 같다. 지금 `projection.py`는 `camera` 역할(웹캠 + 폰 세션)에서 온 답을 버리므로, 디스플레이 페이지는 모든 모드에서 `view` 연결을 따로 하나 열어 화면 값과 캐릭터 상태를 받고 답도 그 연결로 보낸다(`view`에서 온 답은 이미 받는다). 인식 값은 `publish`(웹캠 단독) 또는 `camera`(웹캠 + 폰 세션) 연결로 보낸다.

**"해봤네요"(You tried it)**: 제안이 뜬 때부터 60초 안에 그 대상이 더는 부족하지 않으면(부위는 `segment_explored_ratio`, 높이는 `level_explored_share`, 좌우는 비율 0.2 이상) 캐릭터가 "You tried it"을 5초 띄운다. 캐릭터 상태에 `explored`를 더한다. 제안이 뜬 뒤부터 보므로 O를 만드는 동작은 여기에 들어가지 않는다.

### 5. 디스플레이 화면
- 지금 구성(8자 고리, Space, How you moved, Creative guide)을 유지한다. 인식은 페이지 안에서 하고, 페이지는 자기 방에 보내면서 캐릭터 상태를 돌려받는다.
- 시작할 때 "3초 가만히 서 주세요"와 진행 표시를 크게 띄운다(트래커 캘리브레이션 3초, 라벨의 기준 자리).
- **디버깅 화면**(기본 꺼짐, `D` 키와 버튼으로 켜고 끔, 마지막 상태를 브라우저에 기억)
  - 웹캠 영상과 스켈레톤(거울처럼), 잘 안 보이는 관절은 흐리게
  - 프레임 수, 모델 실행 방식(GPU/CPU), 트래커 상태(맞추는 중/보는 중)
  - 부위별 사용량과 "모름"인 부위, 높이·좌우 비율, 지금 부족한 대상 목록
  - 캐릭터 상태와 타이머(남은 준비 시간, 대상별로 부족이 이어진 시간, 남은 쉬는 시간)
- 입력 고르기(웹캠 / 영상 파일)와 BPM 입력은 디버깅 화면 안에 둔다.
- **글자**: 모두 영어. 화면 글자와 캐릭터 문장을 한 표(`EN`)에 모아 두어, 나중에 `KO` 표와 스위치(오른쪽 위 `EN / KO`)를 더하면 바뀌게 한다. 스위치는 여유가 있을 때 한다.

### 6. 폰 카메라 경로
- `ProjectionCard.tsx`가 `display.ts`의 패킷 함수를 써서 부위별 동작, 공간, 늘어난 `underused`까지 보낸다.
- 폰 단독 카메라 탭의 동작은 바꾸지 않는다.
- 확인은 node 테스트까지 한다. 실기기 확인은 Android 폰이 있을 때 한다.

### 7. 시연 대본 (초안, 리허설에서 맞춘다)

### 8. 오늘의 순서
오늘 전부 끝내는 것을 목표로 하고, 아래 순서로 한다. 앞의 것이 시연에 더 필요하다.
1. 인식: `webEvent.ts` 되살리기, `labels.ts` 옮기기(가려진 부위 처리 포함)와 테스트
2. 머리 위 O(`answer.ts`)와 테스트
3. 패킷 함수(`display.ts`), 묶음 만들기
4. 서버: 새 대상 단어 검사, 캐릭터의 웹캠 규칙·고르는 순서·12초 '아니요'·"You tried it", `camera` 역할의 답 받기
5. 디스플레이 페이지 합치기, 디버깅 화면, `/movement` 넘기기, `movement.js` 지우기
6. 영상 파일과 웹캠으로 리허설, 시연 대본(`docs/DEMO_SCRIPT.md`)
7. 폰 경로(`ProjectionCard`)와 테스트
8. `EN / KO` 스위치

시간이 모자라면 8 → 7 순서로 뺀다. 1–6이 MVP다.

### 9. 확인 방법

## 아직 열린 것
- '예'의 최종 방법(워치 OK / 머리 위 O)은 사용자가 고민 중이다. 이번에는 O를 새로 만들고 워치 길은 있는 그대로 둔다. 둘 다 같은 `agent_response`로 들어가므로 어느 쪽으로 정해도 서버와 화면은 바뀌지 않는다.

## 작성자의 판단 목록
- '예'의 길: 웹캠 모드의 시연 기본은 머리 위 O(폰 없이 되는 유일한 손 안 쓰는 길), 워치는 폰이 붙은 모드에서 지금처럼. 키보드 `Y`는 리허설용(4절).
- 머리 위 O의 조건 값(몸통 길이 0.6, 3초)과 "묻는 동안에만 센다"(4절).
- '아니요'로 보는 시간 12초, O를 만드는 중이면 끝까지 기다림, 지금의 [Not now] 버튼도 남김(4절).
- 끼어들기 규칙은 방을 연 쪽이 아니라 춤을 읽는 쪽을 따른다(4절).
- 디스플레이는 서버 HTML 페이지로 남기고, 인식 코드는 묶음 파일로 넣는다. 묶음 결과는 저장소에 넣는다.
- `/movement`는 `/display`로 넘기고 `movement.js`·`movement.html`·`movement.test.mjs`는 지운다(모두 사용자 코드).
- 세 가지 모드와 주소(1절).
- 가려진 부위는 "모름"으로 두고 비율에서 뺀다(2절).
- `moves.ts`와 `labels.ts`는 이번에는 둘 다 둔다(2절).
- 좌우 부족 기준 0.1, 웹캠 끼어들기 값(15초 / 8초 / 30초 / 60초), 고르는 순서(4절). 모두 리허설에서 맞춘다.
- "해봤네요"의 기준과 60초 창(4절).
- 디버깅 화면의 내용과 기본 꺼짐(5절).
- 폰 경로는 node 테스트까지, 수요일 일(6, 8절).
